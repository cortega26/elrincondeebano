# RFC — Actualización de Vitest y cobertura a 5.0.1

**Fecha:** 2026-10-09
**Origen:** Dependabot PR #469
**Alcance:** solo herramientas de desarrollo y pruebas, Node 24.

## Justificación

Vitest 5 y `@vitest/coverage-v8` 5.0.1 reemplazan la línea 4, manteniendo ambas versiones coordinadas. La actualización evita mantener indefinidamente una versión principal antigua. No modifica código ni dependencias de producción. El paquete `@stryker-mutator/vitest-runner@10.0.0` declara `vitest >=2.0.0`, una compatibilidad nominal que debe verificarse operativamente.

## Riesgos y mitigaciones

- Cambios de comportamiento en runner, transformación o cobertura: ejecutar ambos workspaces de pruebas, compilación y certificación de Content Manager.
- Regresiones de lint, tipado o E2E: verificar CI completa, Playwright y Lighthouse.
- Integridad de `package-lock.json`: conservar paquetes de seguridad ya actualizados, usar `npm ci` determinista; no introducir `npm install` para validación.
- Cambio accidental de catálogo heredado del PR original #469: **excluido** por completo. Solo cambian los dos manifests y el lockfile, además de este RFC.
- Riesgos residuales de pruebas de mutación: el objetivo de compatibilidad del adaptador existe, pero no implica que un score de mutación esté validado; no declarar equivalencia sin esa prueba.

## Migración de tests existentes

Los tests heredados que asignaban directamente \`global.document\` se adaptan sin tocar el storefront: el test de visualización usa un documento local y la suite de controladores utiliza \`vi.stubGlobal\` / \`vi.unstubAllGlobals\` para restauración entre casos. La regresión de Vitest 5 se verificará en CI. Este cambio es específico del runner y no altera aserciones.

## Migración y aceptación

1. Actualizar `vitest` y `@vitest/coverage-v8` conjuntamente en root y admin.
2. Conservar Node 24 y los demás cambios de dependencias menores y seguridad ya integrados.
3. Exigir CI, lint, typecheck, pruebas unitarias, certificación admin, compilación determinista y E2E exitosos sobre el SHA exacto.
4. No integrar ante fallos nuevos atribuibles al cambio de major; investigarlos antes.

## Rollback

Revertir el commit de actualización y revalidar CI. No hay migración de inventario, API, rutas ni datos persistentes.
